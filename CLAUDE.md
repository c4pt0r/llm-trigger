# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Natural language → structured `IF/THEN` trigger rules. An agent (any prompt-in/reply-out CLI — pi with a local model by default, see `src/agent.js`) runs **only at compile time** to translate a sentence into a `{if, then}` JSON rule; the runtime (cron scheduler → poll sources → evaluate conditions → run actions) is plain deterministic code with zero model calls — except rules that opt into the slow-judge ops handled by `src/judge.js`: `script` (local command, fact JSON on stdin, exit 0 = pass) and `agent` (one local-model yes/no call). Judges run only on fresh facts that passed the deterministic conditions; scripts run before the model and short-circuit. Zero npm dependencies — requires Node >= 22.5 (uses built-in `node:sqlite`).

## Commands

```bash
npm test                      # node --test test/run.js
npm start                     # HTTP API + web UI + scheduler on 127.0.0.1:8787
npm run cli -- add "<sentence>"   # compile + store a rule (needs pi available)
npm run cli -- parse "<sentence>" # compile only, don't store
npm run cli -- run <id> --dry     # evaluate without executing actions
npm run cli -- run <id> --all     # ignore dedup, replay all known events
npm run cli -- list | fires <id> | events | actions
```

To run a single test: `node --test --test-name-pattern="<pattern>" test/run.js`.

Tests never call pi or the network — they mock `globalThis.fetch`, use `db.open(":memory:")`, and use `makeOfflineCompiler()` from `parse.js` instead of the real model.

## Architecture

The central invariant: **`src/catalog.js` is the single contract** between the LLM and the runtime. It whitelists sources, events (with fields + dedup key), condition ops, and actions. Three consumers read it:

- `src/parse.js` — embeds the catalog JSON into the compiler system prompt for pi
- `src/schema.js` — `validateRule()` rejects anything not in the catalog; also `evalRule`/`evalCondition` (condition evaluation), `factKey` (dedup key), and `renderRule` (the canonical `IF ... WHEN ... EVERY ... THEN ...` string — generated by code from structured data, never written by the model)
- the engine, via `src/sources.js` (one branch per event: fetch facts from GitHub/HTTP/timer) and `src/actions.js` (log / webhook.post / lark.webhook / shell.exec / agent.run — the last hands the event to the agent in executor mode (`execArgs`, tools enabled) and is `ALLOW_SHELL`-gated like shell.exec)

**Adding an event** = one entry in `catalog.js` + one branch in `sources.js`; prompt and validator pick it up automatically.

`observe.changed` (source `observe`) is the open-world event: target is `{what, url|command}`; `sources.js` snapshots the url (HTML stripped) or command output, the engine passes the previous snapshot from rule state (`db.getSnapshot`/`saveSnapshot`, kept beside `seen` in `state_json`) into `fetchFacts`, and the fact carries `previous`/`content`/`changed`/`digest`. Dedup key = content digest, so unchanged snapshots never reach the judges; for facts carrying a `previous`/`content` pair, `judge.js` injects delta semantics (yes only for things NEWLY present vs `previous`), so a reshuffled page with the same old news does not re-fire. The compiler uses it as fallback when no specific event fits but the user named a URL or command.

Compile path (`parse.js`): pi returns JSON → `validateRule()` → on failure, errors are fed back to the model for one repair round (`maxRounds: 2`) → still invalid = rejected (422 from API); half-valid rules are never stored. The model may also refuse with `{"error": ...}` if the sentence isn't expressible with the catalog.

Fire path (`engine.js` `runRule`): fetch facts → drop keys already in `state_json.seen` → evaluate deterministic `when` conditions → judge `script`/`agent` conditions via `judge.js` (injectable as `opts.judge` for tests) → run action → log every fact to `fires` with status (`baseline`/`fired`/`no_match`/`dry`/`error`/`skipped`). Three deliberate behaviors:

1. **First check is a baseline** — existing events are recorded as `baseline`, not fired (`rule.last_check_at == null`). `force` replays them. Baseline skips the slow judges.
2. **Dedup is once per event, matched or not** — failed actions log `error` but are never auto-retried.
3. **Slow judges run last and at most once per fact** — only after deterministic conditions pass; a judge failure logs `error` and does not fire.

`src/agent.js` is the agent abstraction used by both the compiler and the judges: `LT_AGENT` picks a preset (`pi` default, `claude`) or a JSON config path (`{cmd, args, output, timeoutMs}` with `{system}`/`{user}`/`{model}`-style placeholders; an arg whose placeholder resolves empty is dropped together with its preceding flag). Output modes: `"pi-jsonl"` (pi's `--mode json` stream) or `"text"` (stdout is the reply). The pi preset runs tool-less (`-nt -ns -np -nc --no-session`); model: `LT_MODEL=provider/id` if set, else `$PI_PROVIDER/$PI_MODEL` (only present inside a pi session), else no model flags at all — pi's own configured default applies.

`src/db.js` (SQLite at `data/llm-trigger.db`): `rules` stores `raw` + `if_json`/`then_json` + `rendered`, with `source/event/action/every` flattened into real columns for direct SQL queries. `src/cron.js` is a hand-rolled 5-field UTC cron parser with a due-window check (`cronDue`) so a late scheduler tick doesn't miss a minute.

`src/server.js` is a dependency-free `node:http` server serving `public/index.html` and the JSON API (`POST /api/parse`, `POST /api/rules`, `PUT/PATCH /api/rules/:id`, `POST /api/rules/:id/run`, `GET /api/fires`, `GET /api/catalog`); `src/scheduler.js` ticks every `LT_TICK_MS` ms (default 60000) when `LT_SCHEDULER=on` and logs one line per due check. `llm-trigger serve` blocks in the foreground; `-d` daemonizes (pid + log next to the db). Per-rule cadence is `if.every` (5-field cron, UTC); the default for sentences with no rhythm is `LT_EVERY` (default `*/10 * * * *`). `if.mode: "once"` (default `"recurring"`, stored in the `mode` column) makes a rule disable itself after its first fire.

## Constraints

- Shell-powered capabilities (`shell.exec`, `agent.run`, `script` conditions, `observe` commands) are **on by default**; `ALLOW_SHELL=0` disables them all (`shellAllowed()` in catalog.js). No API auth — server binds `127.0.0.1` and must not be exposed publicly.
- Unauthenticated GitHub polling is limited to 60 req/h; set `GITHUB_TOKEN` to raise it.
- Single-process scheduler, no distributed lock — running two instances fires twice.
- Rules are one event + a conjunction of conditions; no cross-event composition.
- Config via env vars (see `.env.example`); comments/UI strings are a mix of Chinese and English — match the surrounding file.
